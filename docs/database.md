# Database

PostgreSQL 17, SQLAlchemy 2.1 (Declarative, async), Alembic 1.20.

**Current state: four tables (`users`, `staff_sessions`, `vehicles`,
`vehicle_images`) across three migrations.** The remaining business entities -
`Customer`, quotations, the CRM - are planned but not yet modelled; see
[Planned entities](#5-planned-entities-not-yet-created).

There is **no seed data, no demo vehicles and no fake statistics** in this
database by design.

---

## 1. Local setup

### 1.1 Create the role and database

```sql
CREATE ROLE humera WITH LOGIN PASSWORD 'choose-a-dev-password' CREATEDB;
CREATE DATABASE humera_automobile OWNER humera ENCODING 'UTF8';
```

Using a dedicated non-superuser role matters: the application role should not
be able to create databases or bypass permissions.

### 1.2 Configure the connection

The repository-root `.env` (copy from `.env.example`):

```dotenv
DATABASE_URL=postgresql+asyncpg://humera:choose-a-dev-password@localhost:5432/humera_automobile
```

The URL uses an **async driver** (`asyncpg`) because the application uses
`create_async_engine`. Alembic needs a synchronous driver and derives one
automatically via `Settings.sync_database_url` (`asyncpg` -> `psycopg`). There is
no second URL to keep in sync.

### 1.3 Apply migrations

```bash
cd backend
alembic upgrade head
```

### 1.4 Verify

```bash
alembic current      # expect: <revision> (head)
alembic check        # expect: "No new upgrade operations detected."
```

`alembic check` is the important one: it fails if the models and the database
have drifted, which catches an un-migrated model change before it reaches
production.

## 2. Migration workflow

```bash
cd backend

# 1. Change or add a model in app/db/models/, then register it in
#    app/db/models/__init__.py - autogenerate cannot see an unimported model.

# 2. Generate a revision
alembic revision --autogenerate -m "create vehicles table"

# 3. REVIEW the generated file. Autogenerate is a starting point, not a
#    guarantee: it cannot detect renames, and it gets column reordering and
#    some server-default changes wrong.

# 4. Apply
alembic upgrade head

# 5. Confirm no drift
alembic check
```

Other useful commands:

```bash
alembic downgrade -1        # step back one revision
alembic downgrade base      # remove everything
alembic history --verbose  # full revision graph
alembic upgrade head --sql # print SQL without connecting (review first)
alembic current             # which revision is applied
```

`alembic.ini` deliberately leaves `sqlalchemy.url` empty. `alembic/env.py`
injects the URL from application settings, so the password is never written into
a committed file and the app and migrations can never target different
databases.

Generated revisions are formatted and linted automatically by ruff
post-write hooks.

### Adding a model

1. Create `app/db/models/<entity>.py`.
2. Inherit `Base`, plus `UUIDPrimaryKeyMixin` and `TimestampMixin`.
3. Add the class to `ALL_MODELS` in `app/db/models/__init__.py`.
4. Generate and **review** a migration.

Skipping step 3 is the most common way to end up with a model that exists in
code but has no table.

## 3. Conventions

These are enforced centrally in `app/db/base.py` and are not per-table choices.

**Primary key.** UUID v4 on every table (`UUIDPrimaryKeyMixin`). Chosen over
auto-increment integers because an ID can then be generated without a database
round trip, and because IDs from two merged environments never collide. URLs will
expose these IDs, so they are unguessable by construction.

**Timestamps.** Every table gets timezone-aware `created_at` and `updated_at`
with `server_default=now()`; `updated_at` is maintained by `onupdate`. Storing
UTC-aware values avoids the ambiguity that comes with local-time timestamps.

**Constraint naming.** An explicit `NAMING_CONVENTION` dictionary gives every
index, constraint, foreign key and primary key a deterministic name. Without
this, autogenerated names can change between runs, which makes
`DROP CONSTRAINT` migrations unsafe.

**Money.** Vehicle prices and quotations need exact arithmetic and must never
use floating point. Planned approach is `NUMERIC` plus an ISO 4217 currency
code column, so multi-currency export quotations are exact.

**Enums.** Planned approach is a PostgreSQL `ENUM` type (or a lookup table where
values will change often, e.g. lead stages), not free text - lead stages will
drive reporting and must not drift between spellings.

**Soft deletes.** Planned approach is an explicit `deleted_at` on tables where
an audit trail is legally or commercially necessary, not a blanket policy.

**Migrations are append-only.** Once a revision has been applied outside a
developer machine, do not edit it. Add a new revision instead. Editing applied
migrations silently desynchronises environments.

## 4. Current schema

### `users`

Identity only. One table, created by revision `6a6b19f2de08`.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Primary key, v4 |
| `email` | `VARCHAR(320)` | Unique, indexed. RFC 5321 maximum length |
| `phone` | `VARCHAR(32)` | Nullable, indexed. E.164, e.g. `+971501234567` |
| `full_name` | `VARCHAR(200)` | Not null. Name shown to staff in the CRM |
| `password_hash` | `VARCHAR(255)` | Nullable. **Argon2id digest, never plaintext** |
| `is_active` | `BOOLEAN` | Default `true`. Inactive users are blocked at sign-in but retained for audit |
| `is_staff` | `BOOLEAN` | Default `false`. Distinguishes staff from customers; no separate table |
| `email_verified_at` | `TIMESTAMPTZ` | Nullable |
| `last_login_at` | `TIMESTAMPTZ` | Nullable. Drives inactive-account reporting |
| `created_at` | `TIMESTAMPTZ` | Default `now()` |
| `updated_at` | `TIMESTAMPTZ` | Default `now()`, auto-updated |

`password_hash` is nullable so that a staff-invited user or a
WhatsApp-first enquiry contact can exist before they have set a password.

Indexes: `pk_users` (primary key), `ix_users_email` (unique), `ix_users_phone`.

Verified against a live PostgreSQL 17.10 instance via
`upgrade head` -> `downgrade base` -> `upgrade head` -> `alembic check`.

### `vehicles`

Public inventory. One row per vehicle the business has chosen to publish. Created
by revision `f02478f83720`.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Primary key, v4 |
| `slug` | `VARCHAR(200)` | Unique, indexed. Public URL identifier, lower-case and hyphenated |
| `brand` | `VARCHAR(80)` | Not null. Serialised to the API as `make` |
| `model` | `VARCHAR(80)` | Not null |
| `variant` | `VARCHAR(120)` | Nullable, e.g. a trim or engine designation |
| `year` | `SMALLINT` | Not null. `CHECK (year >= 1900)` |
| `body_type` | `VARCHAR(40)` | Nullable |
| `transmission` | `VARCHAR(20)` | Nullable |
| `fuel` | `VARCHAR(20)` | Nullable |
| `colour` | `VARCHAR(40)` | Nullable |
| `mileage_km` | `INTEGER` | Nullable, `>= 0`. Unit is in the name deliberately |
| `vin` | `CHAR(17)` | Nullable, unique. `CHECK` enforces 17 characters and excludes `I`, `O`, `Q` |
| `price` | `NUMERIC(12,2)` | Nullable, `> 0`. `NULL` means "not published" |
| `currency` | `CHAR(3)` | Not null, default `USD`. `CHECK (currency = 'USD')` |
| `availability` | `VARCHAR(20)` | Not null, default `available`. `CHECK` in (`available`, `reserved`, `sold`). Serialised as `status` |
| `location` | `VARCHAR(120)` | Nullable, free text. A real depot FK is deferred until a location table exists |
| `features` | `JSONB` | Nullable flat `{label: value}` object |
| `created_at` | `TIMESTAMPTZ` | Default `now()`, indexed |
| `updated_at` | `TIMESTAMPTZ` | Default `now()`, auto-updated |

Indexes: `pk_vehicles` (primary key), `ix_vehicles_slug` (unique), `ix_vehicles_vin`
(unique), `ix_vehicles_created_at`.

**`brand` and `availability` are renamed to `make` and `status` at the API edge.**
The columns use the business's vocabulary; `VehicleResponse` uses the frontend's,
and `serialization_alias` bridges the two. This is the only translation in the
stack, and it is one line per field on the backend rather than a mapper spread
across the frontend.

### `vehicle_images`

Ordered media for a vehicle. Created by revision `f02478f83720`.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Primary key, v4 |
| `vehicle_id` | `UUID` | → `vehicles.id`, indexed, `ON DELETE CASCADE` |
| `position` | `SMALLINT` | Not null, `>= 0`. Unique per vehicle. **Position 0 is the primary photograph** |
| `src` | `VARCHAR(2048)` | Not null. URL or path served to the browser |
| `alt` | `VARCHAR(200)` | Not null, non-empty. Required: a decorative-only alt is wrong for a vehicle photograph |
| `width` | `INTEGER` | Nullable. Intrinsic size, to prevent layout shift |
| `height` | `INTEGER` | Nullable |
| `created_at` | `TIMESTAMPTZ` | Default `now()` |
| `updated_at` | `TIMESTAMPTZ` | Default `now()`, auto-updated |

Indexes: `pk_vehicle_images` (primary key), `ix_vehicle_images_vehicle_id`,
`uq_vehicle_images_vehicle_position` (unique on `vehicle_id`, `position`).

**There is no `is_primary` flag.** Position `0` *is* the primary photograph.
A second source of truth for "which image is the hero" is a second thing that can
disagree with the first, and the frontend only needs the list in order.

**Images are rows, not a `TEXT[]`.** They are ordered, uniquely positioned per
vehicle, and each carries alt text and dimensions, so an array would be strictly
worse.

**`features` is JSONB, not a `vehicle_features` table.** This is the one
deliberate deviation from the entity list in section 5. Features are a flat
key/value set that is written and read whole, never filtered on, joined or
aggregated. A child table would add a join, an ordering question and a second
migration to solve a problem the business does not have. If a feature ever needs
to be queried ("all automatics under 40,000"), promoting it to a table is a
contained migration - and `docs/architecture.md` records it as the trigger.

Verified against a live PostgreSQL 17.10 instance: `upgrade head`, then
`alembic check` reporting no drift. Constraints were exercised with rolled-back
`INSERT`s confirming that non-USD currencies, zero and negative prices, unknown
availability, malformed VINs and duplicate slugs or VINs are all rejected by the
database itself, not only by the application.

### `staff_sessions`

One authenticated staff browser session. Created by revision
`44e9718a5560`, alongside the archiving columns on `vehicles`.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Primary key, v4 |
| `user_id` | `UUID` | → `users.id`, indexed, `ON DELETE CASCADE` |
| `token_hash` | `CHAR(64)` | SHA-256 hex digest of the session token, **uniquely indexed**. The token itself is never stored |
| `expires_at` | `TIMESTAMPTZ` | Not null. Hard expiry, enforced on every request |
| `last_used_at` | `TIMESTAMPTZ` | Not null. Refreshed at most every `SESSION_LAST_USED_REFRESH_SECONDS` |
| `created_at` | `TIMESTAMPTZ` | Default `now()` |
| `updated_at` | `TIMESTAMPTZ` | Default `now()`, auto-updated |

Indexes: `pk_staff_sessions` (primary key), `ix_staff_sessions_user_id`,
`ix_staff_sessions_token_hash` (unique), `ix_staff_sessions_expires_at`.

**Only the digest is stored.** A database disclosure - a leaked backup, an SQL
injection, a dumped replica - yields digests that cannot be replayed as sessions,
because the token itself is never written down. The digest is indexed and unique
because every authenticated request resolves a session by it.

**Sessions are deleted, not flagged.** A row is a live session, full stop. There
is no `revoked_at`, so there is no state in which a session is simultaneously
invalid and present, and no query that has to remember to exclude it. Sign-out
deletes the row, which is also what makes revocation immediate.

`expires_at` is enforced by the application on every request rather than by a
sweeper, so a lapsed session is refused the moment it lapses.
`python -m app.cli purge_expired_sessions` reclaims rows for storage; it is not
the security mechanism.

`ix_staff_sessions_expires_at` exists so that purge is a range scan rather than a
sequential read of the table.

### Zero rows, and that is correct

`vehicles` and `vehicle_images` contain **no rows**. `docs/architecture.md` is
explicit that no seed data, fake vehicles or fake statistics may exist, and the
business has not published stock. Every example in this file and in `docs/api.md`
is a placeholder showing shape; none of it exists in the database.

`staff_sessions` is also empty, and `users` is empty until an operator runs
`python -m app.cli create_staff`. There is no registration endpoint, so there is
no way for the database to acquire a staff account other than a human running that
command on the server.

An empty inventory is a valid state that the API and the frontend both render
correctly. It is not a failure to be backfilled with sample data.

## 5. Planned entities (not yet created)

`Vehicle` and `VehicleImage` listed here are now real - see section 4. The rest
are specified at a conceptual level only; their columns should be agreed against
real business requirements before being frozen into migration history.

| Entity | Purpose | Key relationships |
| --- | --- | --- |
| `Customer` | Buyer profile, contact and destination preferences | 1-to-1 with `User` for account holders |
| `Vehicle` | Aggregate root for a unit in stock | **Implemented.** Owns images; features are JSONB |
| `VehicleImage` | Ordered media, position 0 is primary | **Implemented.** Many per `Vehicle` |
| `VehicleFeature` | Key/value specification set | **Not implemented.** Currently JSONB on `vehicles`; promote when filtering *by specification* is needed |
| `VehicleInquiry` | Enquiry about a specific vehicle | → `Vehicle`, → `Lead` |
| `SavedVehicle` | Customer's shortlist | Many per `Customer`/`User` |
| `VehicleComparison` | Side-by-side selection | → multiple `Vehicle` |
| `ExportRequest` | International export enquiry | → `Vehicle`, → `Quote` |
| `Quote` | Priced export quotation, versioned | Many per `ExportRequest` |
| `Lead` | CRM pipeline record | Source of `VehicleInquiry` / `ExportRequest` |
| `Notification` | Staff reminders and follow-ups | → staff `User` |
| `AuditLog` | Append-only record of state changes | → actor `User` |

Design notes worth settling before these are implemented:

- Enquiry, comparison and export tables should **reference** a `Vehicle` rather
  than copying its fields, so a price or availability change can never go stale
  in one place. `vehicles.slug` being unique is what makes such a reference
  stable and human-readable.
- `Quote` rows should be versioned, not overwritten. A customer disputing a
  landed-cost figure months later is a realistic scenario in vehicle export.
- `AuditLog` and a staff-permission model are prerequisites to designing
  *before* the first real customer record is stored, not after. Note that the
  vehicle tables are already live and have no write path, so there is currently
  nothing to audit.
- Destination-specific duty and shipping data will be configuration referenced
  by the quote calculation, never hard-coded in a service.
- `vehicles.location` is free text for now. It becomes a FK to a `Location` table
  when stock is actually held at more than one depot, which is also when a
  customer would start filtering by it.

## 6. Production notes (not yet actioned)

Deployment and operations are out of scope for Step 1. When that step begins:

- Migrations run as a separate job before the new application version starts -
  never on application start-up, which would race across multiple replicas.
- Backups and point-in-time recovery configured and **restore-tested**.
- Application role granted only the privileges it needs; no superuser.
- Connection pool sized against the database's `max_connections` and the number
  of API replicas.
- `alembic check` run in CI to fail a build on schema drift.
