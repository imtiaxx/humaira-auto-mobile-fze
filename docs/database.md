# Database

PostgreSQL 17, SQLAlchemy 2.1 (Declarative, async), Alembic 1.20.

**Current state: one table (`users`) and one migration.** The remaining
business entities are planned but not yet modelled - see
[Planned entities](#planned-entities-not-yet-created).

There is **no seed data, no demo vehicles and no fake statistics** in this
database by design.

---

## 1. Local setup

### 1.1 Create the role and database

```sql
CREATE ROLE humera WITH LOGIN PASSWORD 'choose-a-dev-password' CREATEDB;
CREATE DATABASE humera_automobile OWNER humera ENCODING 'UTF8';
```

Using a dedicated non-superuser role matters: the application role should not
be able to create databases or bypass permissions.

### 1.2 Configure the connection

The repository-root `.env` (copy from `.env.example`):

```dotenv
DATABASE_URL=postgresql+asyncpg://humera:choose-a-dev-password@localhost:5432/humera_automobile
```

The URL uses an **async driver** (`asyncpg`) because the application uses
`create_async_engine`. Alembic needs a synchronous driver and derives one
automatically via `Settings.sync_database_url` (`asyncpg` -> `psycopg`). There is
no second URL to keep in sync.

### 1.3 Apply migrations

```bash
cd backend
alembic upgrade head
```

### 1.4 Verify

```bash
alembic current      # expect: <revision> (head)
alembic check        # expect: "No new upgrade operations detected."
```

`alembic check` is the important one: it fails if the models and the database
have drifted, which catches an un-migrated model change before it reaches
production.

## 2. Migration workflow

```bash
cd backend

# 1. Change or add a model in app/db/models/, then register it in
#    app/db/models/__init__.py - autogenerate cannot see an unimported model.

# 2. Generate a revision
alembic revision --autogenerate -m "create vehicles table"

# 3. REVIEW the generated file. Autogenerate is a starting point, not a
#    guarantee: it cannot detect renames, and it gets column reordering and
#    some server-default changes wrong.

# 4. Apply
alembic upgrade head

# 5. Confirm no drift
alembic check
```

Other useful commands:

```bash
alembic downgrade -1        # step back one revision
alembic downgrade base      # remove everything
alembic history --verbose  # full revision graph
alembic upgrade head --sql # print SQL without connecting (review first)
alembic current             # which revision is applied
```

`alembic.ini` deliberately leaves `sqlalchemy.url` empty. `alembic/env.py`
injects the URL from application settings, so the password is never written into
a committed file and the app and migrations can never target different
databases.

Generated revisions are formatted and linted automatically by ruff
post-write hooks.

### Adding a model

1. Create `app/db/models/<entity>.py`.
2. Inherit `Base`, plus `UUIDPrimaryKeyMixin` and `TimestampMixin`.
3. Add the class to `ALL_MODELS` in `app/db/models/__init__.py`.
4. Generate and **review** a migration.

Skipping step 3 is the most common way to end up with a model that exists in
code but has no table.

## 3. Conventions

These are enforced centrally in `app/db/base.py` and are not per-table choices.

**Primary key.** UUID v4 on every table (`UUIDPrimaryKeyMixin`). Chosen over
auto-increment integers because an ID can then be generated without a database
round trip, and because IDs from two merged environments never collide. URLs will
expose these IDs, so they are unguessable by construction.

**Timestamps.** Every table gets timezone-aware `created_at` and `updated_at`
with `server_default=now()`; `updated_at` is maintained by `onupdate`. Storing
UTC-aware values avoids the ambiguity that comes with local-time timestamps.

**Constraint naming.** An explicit `NAMING_CONVENTION` dictionary gives every
index, constraint, foreign key and primary key a deterministic name. Without
this, autogenerated names can change between runs, which makes
`DROP CONSTRAINT` migrations unsafe.

**Money.** Vehicle prices and quotations need exact arithmetic and must never
use floating point. Planned approach is `NUMERIC` plus an ISO 4217 currency
code column, so multi-currency export quotations are exact.

**Enums.** Planned approach is a PostgreSQL `ENUM` type (or a lookup table where
values will change often, e.g. lead stages), not free text - lead stages will
drive reporting and must not drift between spellings.

**Soft deletes.** Planned approach is an explicit `deleted_at` on tables where
an audit trail is legally or commercially necessary, not a blanket policy.

**Migrations are append-only.** Once a revision has been applied outside a
developer machine, do not edit it. Add a new revision instead. Editing applied
migrations silently desynchronises environments.

## 4. Current schema

### `users`

Identity only. One table, created by revision `6a6b19f2de08`.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Primary key, v4 |
| `email` | `VARCHAR(320)` | Unique, indexed. RFC 5321 maximum length |
| `phone` | `VARCHAR(32)` | Nullable, indexed. E.164, e.g. `+971501234567` |
| `full_name` | `VARCHAR(200)` | Not null. Name shown to staff in the CRM |
| `password_hash` | `VARCHAR(255)` | Nullable. **Argon2id digest, never plaintext** |
| `is_active` | `BOOLEAN` | Default `true`. Inactive users are blocked at sign-in but retained for audit |
| `is_staff` | `BOOLEAN` | Default `false`. Distinguishes staff from customers; no separate table |
| `email_verified_at` | `TIMESTAMPTZ` | Nullable |
| `last_login_at` | `TIMESTAMPTZ` | Nullable. Drives inactive-account reporting |
| `created_at` | `TIMESTAMPTZ` | Default `now()` |
| `updated_at` | `TIMESTAMPTZ` | Default `now()`, auto-updated |

`password_hash` is nullable so that a staff-invited user or a
WhatsApp-first enquiry contact can exist before they have set a password.

Indexes: `pk_users` (primary key), `ix_users_email` (unique), `ix_users_phone`.

Verified against a live PostgreSQL 17.10 instance via
`upgrade head` -> `downgrade base` -> `upgrade head` -> `alembic check`.

## 5. Planned entities (not yet created)

Named here and in `app/db/models/__init__.py` so the intended model is
unambiguous. **None of these tables exist.** They are specified here at a
conceptual level only; the actual columns should be agreed against real
business requirements before being frozen into migration history.

| Entity | Purpose | Key relationships |
| --- | --- | --- |
| `Customer` | Buyer profile, contact and destination preferences | 1-to-1 with `User` for account holders |
| `Vehicle` | Aggregate root for a unit in stock | Owns images and features |
| `VehicleImage` | Ordered media, one flagged primary | Many per `Vehicle` |
| `VehicleFeature` | Key/value specification set | Many per `Vehicle` |
| `VehicleInquiry` | Enquiry about a specific vehicle | → `Vehicle`, → `Lead` |
| `SavedVehicle` | Customer's shortlist | Many per `Customer`/`User` |
| `VehicleComparison` | Side-by-side selection | → multiple `Vehicle` |
| `ExportRequest` | International export enquiry | → `Vehicle`, → `Quote` |
| `Quote` | Priced export quotation, versioned | Many per `ExportRequest` |
| `Lead` | CRM pipeline record | Source of `VehicleInquiry` / `ExportRequest` |
| `Notification` | Staff reminders and follow-ups | → staff `User` |
| `AuditLog` | Append-only record of state changes | → actor `User` |

Design notes worth settling before these are implemented:

- Enquiry, comparison and export tables should **reference** a `Vehicle` rather
  than copying its fields, so a price or availability change can never go stale
  in one place.
- `Quote` rows should be versioned, not overwritten. A customer disputing a
  landed-cost figure months later is a realistic scenario in vehicle export.
- `AuditLog` and a staff-permission model are prerequisites to designing
  *before* the first real customer record is stored, not after.
- Destination-specific duty and shipping data will be configuration referenced
  by the quote calculation, never hard-coded in a service.

## 6. Production notes (not yet actioned)

Deployment and operations are out of scope for Step 1. When that step begins:

- Migrations run as a separate job before the new application version starts -
  never on application start-up, which would race across multiple replicas.
- Backups and point-in-time recovery configured and **restore-tested**.
- Application role granted only the privileges it needs; no superuser.
- Connection pool sized against the database's `max_connections` and the number
  of API replicas.
- `alembic check` run in CI to fail a build on schema drift.
